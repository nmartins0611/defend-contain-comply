= Module 3: COMPLY — Secure Supply Chain
:source-highlighter: rouge
:toc: macro
:toclevels: 1

toc::[]

The vulnerability is patched and the system is hardened. Now Meridian Financial's platform team needs to deliver an immutable, containerized version of the application — with provenance, scanning, and registry delivery automated by AAP.

This module demonstrates how Ansible Automation Platform extends beyond configuration management into container supply chain automation using Podman on RHEL.

== Learning objectives

By the end of this module, you'll be able to:

* Build a hardened container image from a Jinja2-templated Containerfile
* Run basic image security checks via Ansible
* Push a verified image to a local container registry
* Validate the container serves the application correctly

== Exercise 1: Review the Containerfile

The application container is built from a UBI 9 minimal base, installs only the patched `httpd`, and runs as a non-root user.

. Examine the Containerfile template:
+
[source,role="execute"]
----
cat /var/lib/awx/projects/defend-contain-comply/templates/Containerfile.j2
----
+
Key security properties:
+
* Based on `registry.access.redhat.com/ubi9/ubi-minimal` (Red Hat trusted base)
* Installs only `httpd` and `mod_ssl` — minimal attack surface
* Runs as `apache` user (non-root)
* Labels include advisory and remediation metadata

. Review the hardened httpd configuration that will be embedded:
+
[source,role="execute"]
----
cat /tmp/container-build/httpd.conf 2>/dev/null || echo "Build context not yet created — will be generated by playbook."
----

=== Verify

The Containerfile uses UBI minimal, installs minimal packages, and runs as non-root.

== Exercise 2: Build the Container Image

Run the AAP playbook that builds the container image using Podman.

. In AAP Controller, navigate to **Job Templates** and launch "Build Hardened Container":
+
Or from the terminal:
+
[source,role="execute"]
----
cd /var/lib/awx/projects/defend-contain-comply
ansible-playbook playbooks/comply/build-container.yml -i inventory/workshop.yml -e "target_advisory=RHSA-2024:5138"
----

. Verify the image was created:
+
[source,role="execute"]
----
podman images | grep meridian-app
----
+
You should see the image tagged with today's date and `latest`.

. Inspect the image labels:
+
[source,role="execute"]
----
podman inspect localhost:5000/meridian-app:latest --format '{{range $k,$v := .Config.Labels}}{{$k}}: {{$v}}{{"\n"}}{{end}}'
----
+
Note the `security.remediated` and `security.advisory` labels — these provide provenance.

=== Verify

* Image `localhost:5000/meridian-app` exists with correct tags
* Labels include advisory metadata
* Image size is minimal (UBI minimal base)

== Exercise 3: Scan the Container Image

Run security checks against the built image.

. Launch the scan playbook:
+
[source,role="execute"]
----
ansible-playbook playbooks/comply/scan-image.yml -i inventory/workshop.yml
----

. Review the scan results:
+
[source,role="execute"]
----
cat /tmp/container-scan-results/image-metadata.txt
----

. Verify the container runs as non-root:
+
[source,role="execute"]
----
podman inspect localhost:5000/meridian-app:latest --format '{{.Config.User}}'
----
+
Expected: `apache`

. Check the package list inside the image:
+
[source,role="execute"]
----
wc -l /tmp/container-scan-results/image-packages.txt
----
+
A minimal image should have far fewer packages than the host system.

=== Verify

* Container user is `apache` (non-root confirmed)
* Image metadata report generated
* Package count is minimal compared to full RHEL

== Exercise 4: Push to Registry and Verify

Deliver the image to the trusted local registry and validate it serves traffic.

. Ensure the local registry is running:
+
[source,role="execute"]
----
podman ps | grep registry || podman run -d --name workshop-registry -p 5000:5000 -v registry-data:/var/lib/registry docker.io/library/registry:2
----

. Push the image:
+
[source,role="execute"]
----
podman push localhost:5000/meridian-app:latest --tls-verify=false
----

. Verify it landed in the registry:
+
[source,role="execute"]
----
curl -s http://localhost:5000/v2/meridian-app/tags/list | python3 -m json.tool
----

. Run the container and test it serves content:
+
[source,role="execute"]
----
podman run -d --name meridian-app-test -p 8443:8443 localhost:5000/meridian-app:latest
----

. Verify the application responds:
+
[source,role="execute"]
----
curl -s http://localhost:8443/ | grep "Meridian Financial"
----
+
Expected: The HTML page confirms the hardened application is running.

. Clean up the test container:
+
[source,role="execute"]
----
podman stop meridian-app-test && podman rm meridian-app-test
----

=== Verify

* Image is available in the local registry
* Container starts and serves the application content
* The response includes "Meridian Financial" confirming correct content delivery

== Module summary

You've successfully completed the COMPLY module.

**What you accomplished:**

* Built a hardened container from a templated Containerfile using AAP
* Ran image security scans confirming non-root execution and minimal packages
* Pushed the verified image to a local registry
* Validated end-to-end that the container serves the application

**Key takeaways:**

* AAP extends naturally into container supply chain workflows via `containers.podman`
* Labels provide provenance — tying the image back to the specific advisory and remediation
* Non-root containers are a baseline security requirement, easily enforced in Containerfiles
* Local registries provide a trust boundary for image distribution

**Complete lifecycle:**
You've now managed a vulnerability from initial detection (DEFEND) through policy-gated remediation (CONTAIN) to immutable container delivery (COMPLY) — all orchestrated by Ansible Automation Platform.
